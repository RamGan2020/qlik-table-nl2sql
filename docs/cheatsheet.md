# Шпаргалка: работа с инструментом NL → SQL (qlik-table-nl2sql)

Инструмент отвечает на вопросы по базе финансовой отчётности застройщика обычным русским языком. Вы пишете вопрос — получаете SQL и таблицу с цифрами. Под капотом: PostgreSQL (Docker) + MCP-сервер + модель Kimi.

---

## 1. Быстрый старт (первый раз, ~10 минут)

```bash
# 1. База данных (из корня проекта D:\Работа\js\qlik_table)
docker compose up -d

# 2. MCP-сервер
cd mcp-server
npm install
cp .env.example .env      # Windows: скопировать вручную
# открыть .env и вставить MOONSHOT_API_KEY (подписка Kimi Code — ключ из
# https://www.kimi.com/code/console, далее см. mcp-server/README.md)

npm test                  # должно быть 6 PASS
```

Дальше работа идёт в **Kimi Code CLI**: открыть сессию в папке проекта, набрать `/mcp` — в списке должен быть `qlik-table-nl2sql` со статусом ok. Всё, можно спрашивать.

Если инструментов нет в списке — сессия создана до настройки: наберите `/new`.

---

## 2. Как задавать вопросы

Просто пишите по-русски, как коллеге. Чем точнее формулировка, тем точнее ответ. Четыре вещи, которые резко повышают качество:

| Приём | Плохо | Хорошо |
|---|---|---|
| Период явно | «продажи осенью» | «продажи за сентябрь–ноябрь 2026» |
| Точные названия | «по заречному» | «по ЖК «Заречный»» |
| Единицы | «цена» | «средняя цена за м², в тысячах рублей» |
| Формат ответа | «каналы» | «топ-5 каналов по выручке, с долей в процентах» |

Дополнительно:

- **Один вопрос — одна задача.** Не «покажи продажи, план и остатки по всем объектам», а три вопроса подряд.
- **Сложный анализ — просите декомпозицию:** слово «разложи на факторы» включает режим факторного анализа (см. раздел 5).
- **Сомневаетесь в цифре** — попросите: «покажи SQL» или «выполни запрос отдельно». SQL видно всегда, его можно проверить.
- **Формулировки-синонимы** понимаются: «выручка» = «продали на» = «реализация»; «пришло денег» = «поступления» (см. словарь в разделе 3).

Типичное время ответа: **30 секунд — 2 минуты** на вопрос (зависит от модели). Это ad-hoc аналитика, не дашборд в реальном времени.

## 3. Словарь терминов (как система понимает слова)

Каноническое описание данных живёт в YAML-моделях `mcp-server/src/models/*.yaml` и реестре связей `mcp-server/src/relationships.yaml`, подмешивается в каждый запрос. Правила заполнения моделей — [`mcp-server/src/models/README.md`](../mcp-server/src/models/README.md). Главные термины:

| Термин | Что это | Важно помнить |
|---|---|---|
| **Выручка (продажи, реализация)** | Сумма цен сделок по дате договора (`sales.price`) | Не путать с деньгами на счёте — см. поступления |
| **План продаж** | `sales_plan.plan_revenue` по месяцам, ведётся по корпусам и каналам | План есть и в будущих месяцах |
| **Выполнение плана** | 100 × факт / план | Факт считается только по прошедшим месяцам |
| **Средняя цена за м²** | Взвешенная: сумма цен / сумма площадей | НЕ простое среднее цен сделок |
| **Поступления (пришло денег, собрано)** | `cashflow.fact_income` | Платежи растянуты во времени: транши по ходу строительства, рассрочка. Это не выручка |
| **Затраты на строительство** | `construction_progress.fact_cost` по корпусам | Только стройка, без коммерческих расходов |
| **Чистый денежный поток (ЧДП)** | Поступления − затраты по `cashflow` | |
| **Готовность корпуса** | `fact_pct` за последний месяц, % нарастающим итогом | Проценты по месяцам не суммируются |
| **Остаток квартир** | `status = 'available'` | Брони (`reserved`) считаются отдельно |
| **Сделка** | Строка в `sales` | Типы договоров: ДДУ, уступка права, рассрочка |

Что есть в данных:

- **3 объекта:** ЖК «Северный парк» (строится, продажи с 07.2024), ЖК «Заречный» (строится, продажи с 05.2026), ЖК «Городской квартал» (сдан 09.2026, продажи с 10.2023).
- **5 каналов:** сайт застройщика, офис продаж, агентства недвижимости, ипотечный брокер, рекламные площадки.
- **Период данных:** 2023–2028; факт продаж — до текущего месяца, план — в т.ч. на будущее.

## 5. Факторный анализ (режим «почему»)

Если нужен не ответ, а объяснение отклонения, используйте шаблон:

> **«Почему [метрика] за [период] отличается от [план/прошлый период]? Разложи отклонение на факторы: [список разрезов]»**

Пример (реально прогнан): «Почему в октябре 2026 факт продаж ниже плана? Разложи отклонение на факторы: объекты, каналы, цена и количество».

Что получите — цепочку шагов с промежуточными цифрами:

1. **Где** отклонение (по объектам): октябрь 2026 → недобор 5.0 млн, весь — ЖК «Заречный».
2. **Кто** виноват (по каналам): ипотечный брокер −10.2, офис −6.5, агентства −3.4, сайт +0.8, реклама +14.2 (не была в плане).
3. **Что** произошло (объём/цена): продали 8 квартир вместо 9 → −4.9 млн; цена/м² на плане → −0.1 млн.

Итог: «недобор объёмный, причина — провал брокера и офиса, перекрытый незапланированными продажами с рекламы». Все суммы считаются SQL-запросами (не «в уме» модели) и сходятся: −4.9 − 0.1 = −5.0.

На глубокий анализ уходит 3–5 запросов, **5–10 минут** вместо часа аналитика.

## 6. Ограничения — важно понимать

- **Модель может ошибаться.** На простых и средних вопросах — редко, на хитрых (оконные функции, многопроходные агрегации) — бывает. Для управленческих решений критичные цифры перепроверяйте: попросите показать SQL и выполнить его отдельно.
- **Скорость** 30 с – 2 мин на вопрос. Не для интерактивных дашбордов.
- **Факт только по прошедшим месяцам**; в будущих месяцах есть план без факта — сравнивайте корректно.
- **Данные тестовые** (сгенерированы скриптом `db/seed.sql`, детерминировано). Для боевых цифр замените источник данных.
- **Read-only**: инструмент умеет только читать (SELECT). Изменить данные через него нельзя — это защита, а не ограничение.

## 7. Если что-то пошло не так

| Симптом | Решение |
|---|---|
| В `/mcp` сервера нет или статус failed | Набрать `/new`; проверить, что Docker с Postgres запущен (`docker compose ps` в корне проекта) |
| Ошибка 401 | Ключ в `mcp-server/.env` не подходит к endpoint — см. «Два варианта ключей» в `mcp-server/README.md` |
| Отвечает очень долго (2+ мин) | В `.env` поставить `MOONSHOT_MODEL=k3-256k` (быстрая модель), затем `/new` |
| Цифра выглядит странно | Переформулируйте вопрос точнее; попросите «покажи SQL» и проверьте логику вручную |
| Спрашиваю про новые таблицы — не знает | Агенту: «обнови схему БД» (инструмент `refresh_schema`); структура БД менялась? |
| Нужен новый термин/метрика | Допишите меру в соответствующий файл `mcp-server/src/models/*.yaml` (синонимы + SQL) — подхватится без перезапуска |

## 8. Аналитикам: как развивать семантическое ядро

Модели данных — в `mcp-server/src/models/*.yaml` (по файлу на таблицу), связи для JOIN — в `mcp-server/src/relationships.yaml`. Это живой словарь компании. Сценарий: руководство спросило новым словом («доля рассрочки») → аналитик добавляет меру в модель `sales`:

```yaml
- name: installment_share_pct
  label: Доля рассрочки, %
  type: simple
  sql: "100.0 * COUNT(*) FILTER (WHERE contract = 'Рассрочка') / NULLIF(COUNT(*), 0)"
  synonyms: ["доля рассрочки", "сколько купили в рассрочку"]
```

Сохранили файл — следующий вопрос уже видит новое определение (перезапуск не нужен; если YAML битый, сервер продолжит со старой версией и напишет предупреждение). Новая таблица — новый файл в `models/` плюс связи в `relationships.yaml`. Чем полнее синонимы, тем точнее понимание формулировок руководства.

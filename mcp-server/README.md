# qlik-table-nl2sql

MCP-сервер: вопрос на естественном языке (русский) → SQL-запрос по базе финансовой отчётности застройщика (PostgreSQL), с возможностью read-only выполнения.

> Для пользователей (руководство, аналитики): подробная шпаргалка — [`../docs/cheatsheet.md`](../docs/cheatsheet.md). Этот README — техническая документация.

## Инструменты

| Инструмент | Вход | Выход |
|---|---|---|
| `nl_to_sql` | вопрос на русском, напр. «Продажи по каналам за 2026 год» | `{ "sql": "...", "explanation": "..." }` (SQL не выполняется) |
| `execute_sql` | одиночный `SELECT` (допускается `WITH`) | колонки + строки результата (максимум `MAX_ROWS`, по умолчанию 1000) |
| `refresh_schema` | — | перечитывает структуру таблиц из БД (вызывать после изменений DDL) |

Схема БД сервер получает сам: при старте интроспекция `information_schema` + число строк по каждой таблице. Если БД недоступна — использует зашитую статичную схему.

## Как пользоваться (пошагово)

### Шаг 1. Одноразовая настройка (если ещё не сделана)

```bash
# 1. База данных в Docker (из корня проекта)
docker compose up -d

# 2. Зависимости сервера
cd mcp-server
npm install

# 3. Конфигурация: скопировать шаблон и прописать ключ
cp .env.example .env
# открыть .env и вставить MOONSHOT_API_KEY

# 4. Проверка
npm test
```

Минимально рабочий `.env` (подписка Kimi Code):

```
MOONSHOT_API_KEY=sk-...                        # ключ из https://www.kimi.com/code/console
MOONSHOT_BASE_URL=https://api.kimi.ai/coding/v1
MOONSHOT_MODEL=k3-256k
```

### Шаг 2. Открыть сессию Kimi Code в папке проекта

MCP-сервер регистрируется из `.kimi-code/mcp.json` автоматически при **создании** сессии — если сессия уже открыта, перезапустите её (новый чат). Проверить, что сервер подключён: команда `/mcp` — в списке должен быть `qlik-table-nl2sql` со статусом ok.

### Шаг 3. Задать вопрос обычным сообщением

Ничего специального набирать не нужно — просто спросите по-русски. Агент сам вызовет `nl_to_sql`, получит SQL, при необходимости выполнит его через `execute_sql` и покажет таблицу с результатом.

Продажи и каналы:

### Шаг 5. Работа с результатом

- Если SQL выглядит подозрительно — попросите: «перегенерируй запрос» или сформулируйте точнее (добавьте период, объект, единицы измерения).
- Сгенерированный SQL можно выполнить отдельно: «выполни этот SQL» — сработает `execute_sql`.
- Изменили структуру таблиц (DDL)? Скажите «обнови схему БД» — агент вызовет `refresh_schema`, иначе `nl_to_sql` будет видеть старую структуру до перезапуска.

## Как это работает

```
Ваш вопрос (русский)
      │
      ▼
nl_to_sql ──► Moonshot/Kimi (промпт = схема БД + бизнес-правила + пример)
      │            │
      │            ▼
      │       {"sql": "SELECT ...", "explanation": "..."}
      │            │
      ▼            ▼
guard.js (только SELECT?) ──да──► execute_sql ──► PostgreSQL (read-only сессия)
                                          │
                                          ▼
                              колонки + строки результата
```

Один вопрос обрабатывается 1–2 минуты (вызов LLM). База должна быть запущена: `docker compose ps` в корне проекта.

## Семантическое ядро (YAML-модели)

Каноническое описание данных — в `mcp-server/src/models/*.yaml` (по файлу на таблицу) и `mcp-server/src/relationships.yaml` (связи для JOIN). Ядро подмешивается в промпт модели перед каждым вызовом: модель выбирает меру по названию или синониму и использует её канонический SQL, а цепочки джойнов берёт из реестра связей. Рядом с ядром в системный промпт подмешиваются few-shot примеры «вопрос -> эталонный SQL» из `eval/questions.json` (`src/examples.js`): модель берёт с них стиль — алиасы, форматы чисел, фильтры дат, цепочки JOIN.

## От свободного SQL к плану (IR) + компиляции

Модель **не пишет SQL**. Она отвечает строгим JSON-планом (IR): модель-факта (`from`), список `select` (измерения и меры по именам из семантического ядра + `scale`/`round` для форматов), фильтры `where` (по измерению — в WHERE, по мере — в HAVING), `group_by`, `order_by`, `limit`. Схема плана — `src/ir.js` (zod), невалидный план отклоняется с причиной и одним исправляющим повтором.

`src/compiler.js` детерминированно компилирует план в SQL через `@polyglot-sql/sdk` (Rust/WASM, SQLGlot-подобный движок для Node):

- алиасы таблиц фиксированы (`s`, `u`, `b`, `o`, `sp`, `cf`, `p`, `d`) — один план всегда даёт один и тот же SQL побайтово;
- джойны — кратчайшие пути от факта к нужным таблицам по графу `relationships.yaml` (BFS, отсортированная адъяцентность), промежуточные таблицы пути включаются автоматически, лишних джойнов нет;
- фрагменты мер/измерений из YAML квалифицированы именами таблиц и подставляются AST-проходом (`renameTables`), голые колонки не создают неоднозначностей;
- литералы экранируются, значения проверяются по типам и доменам измерений (`domain` в YAML);
- сгенерированный SQL проходит `parse` + `generate` (PostgreSQL-диалект) — синтаксически некорректный SQL наружу не уходит;
- свободный SQL недопустим: невыразимое в IR — честный отказ `unanswerable`, а не выдуманный запрос.

Планы двух видов (`src/ir.js`, zod):

- **v1 — одна модель-факт**: `from`, `select` (измерения/меры по именам + `scale`/`round`), `where` (по измерению → WHERE, по мере → HAVING; value может быть выражением — фильтры «мера против меры»), `group_by`, `order_by`, `limit`. `latest_snapshot`-меры компилируются в `DISTINCT ON`.
- **v2 — подпланы**: `with` строит CTE (каждый подплан — запрос по одной модели), `join` соединяет их (`left/right/full/inner/cross`, пары колонок `on`), внешний `select`/`where` оперируют колонками CTE и `expr` — выражениями из чисел, колонок, арифметики (`+ - * /`) и `coalesce`. Покрывает сравнение плана и факта, факторный анализ (cross join подпланов-строк) и другие многофактовые задачи.

Ответ `nl_to_sql` содержит `sql`, `plan` и `explanation`.

Структура модели (пример — `src/models/sales.yaml`):

- `name`, `label`, `description`, `physical.table`, `physical.primary_key`;
- `dimensions` — атрибуты: `name`, `label`, `type`, `synonyms`;
- `measures` — меры: `name`, `label`, тип (`simple` — готовый SQL; `ratio` — `numerator_sql`/`denominator_sql`; `derived` — выражение; `latest_snapshot` — срез последнего месяца по `snapshot_key` с сортировкой `order_by`), поле `sql`, `synonyms`, `requires_join`, `notes`.

Ключевые свойства:

- **Автообновление без перезапуска:** сервер следит за отпечатком файлов (mtime) и перечитывает модели перед каждым вопросом. Правка применяется со следующего запроса.
- **Отказоустойчивость:** битый YAML не применяется — работает последняя рабочая версия, предупреждение в stderr.
- **Без моделей** сервер работает в ограниченном режиме (физическая схема + базовые правила).

Добавить меру — элемент в `measures` своей модели:

```yaml
- name: installment_share_pct
  label: Доля рассрочки, %
  type: simple
  sql: "100.0 * COUNT(*) FILTER (WHERE contract = 'Рассрочка') / NULLIF(COUNT(*), 0)"
  synonyms: ["доля рассрочки", "сколько купили в рассрочку"]
```

Новая таблица — новый файл в `models/` плюс её связи в `relationships.yaml`. Синонимы — главный приём: они связывают словесные обороты руководства с каноническими определениями.

## Устранение неполадок

| Симптом | Причина | Решение |
|---|---|---|
| `401 Invalid Authentication` | Ключ и endpoint не соответствуют друг другу | Ключ подписки (`sk-kimi...`) → `api.kimi.ai/coding/v1`; ключ платформы → `api.moonshot.ai/v1` |
| `400 invalid temperature` | Модель не принимает заданную температуру | Для `kimi-for-coding` держите `MOONSHOT_TEMPERATURE=1` |
| Инструментов нет в сессии | Сессия открыта до добавления MCP | Перезапустите сессию, проверьте `/mcp` |
| `execute_sql: connect ECONNREFUSED` | База не запущена | `docker compose up -d` в корне проекта |
| `nl_to_sql` отвечает про старые таблицы | Схема закэширована | Скажите агенту «обнови схему БД» (refresh_schema) или перезапустите сессию |
| Ответ модели очень долгий | Рассуждающая модель | Поставьте `MOONSHOT_MODEL=k3-256k` в `.env` |

## Переменные окружения

| Переменная | По умолчанию | Описание |
|---|---|---|
| `MOONSHOT_API_KEY` | — (обязательна для `nl_to_sql`) | Ключ API |
| `DATABASE_URL` | `postgres://postgres:postgres@localhost:5433/qlik_table` | Подключение к БД |
| `MOONSHOT_BASE_URL` | `https://api.moonshot.ai/v1` | OpenAI-совместимый endpoint |
| `MOONSHOT_MODEL` | `kimi-k3` | Модель |
| `MOONSHOT_TEMPERATURE` | `1` | Температура. Coding-модели Kimi допускают только `1`, поэтому детерминированность «один вопрос = один SQL» обеспечивает кэш (`NL2SQL_CACHE`), а не сэмплинг |
| `MAX_ROWS` | `1000` | Лимит строк в `execute_sql` |
| `NL2SQL_TRACE` | — (выключено) | Файл для полной трассировки `nl_to_sql`: вопрос, семантический блок, системный промпт, рассуждение модели (`reasoning_content`), сырой ответ LLM, путь разбора, guard, пост-валидация, итог. Относительный путь — от cwd сервера |
| `NL2SQL_CACHE` | `mcp-server/nl2sql-cache.json` | Файл-кэш сгенерированных SQL. Повторный вопрос (verbatim) возвращает тот же SQL без вызова LLM. `0` — выключить. Ключ включает схему, семантический блок и блок примеров: их смена инвалидирует записи |
| `NL2SQL_EXAMPLES` | включено | Few-shot примеры в промпте `nl_to_sql`: вопросы и эталонные SQL из `eval/questions.json` подмешиваются в системный промпт (сортировка от простых к сложным, автоперечитывание при правке файла). `0` — выключить, например для независимого прогона eval |

Два варианта ключей:

- **Kimi Code membership** (подписка, ключ в [Kimi Code Console](https://www.kimi.com/code/console), формат `sk-kimi...`): `MOONSHOT_BASE_URL=https://api.kimi.ai/coding/v1`, модели `kimi-for-coding`, `k3`, `k3-256k`, `k3.1-pro` (по тарифу). Замечание: `kimi-for-coding` отвечает 1–2 минуты (рассуждающая модель) и требует `MOONSHOT_TEMPERATURE=1`; для более быстрых ответов используйте `k3-256k`.
- **Moonshot Platform** (pay-as-you-go, ключ в [platform.moonshot.ai](https://platform.moonshot.ai)): `MOONSHOT_BASE_URL=https://api.moonshot.ai/v1`, актуальные имена моделей — в документации платформы.

## Оценка качества (eval)

`eval/questions.json` — 40 кейсов (10 простых / 15 средних / 15 сложных) с эталонным SQL. Раннер гоняет каждый вопрос через живой сервер: `nl_to_sql` → выполнение → сравнение с эталоном (позиционное, числа с допуском 1.5%, месяцы-даты приводятся к `YYYY-MM`).

Внимание: эти же 40 вопросов по умолчанию подмешиваются в промпт как few-shot примеры, поэтому для независимой оценки качества прогоняйте eval с `NL2SQL_EXAMPLES=0` (иначе eval частично измеряет «узнавание» эталонов, а не перенос стиля на новые вопросы).

```bash
npm run eval                 # весь набор, ~5-10 минут, пишет eval/report.json
npm run eval -- --level 3    # только сложные
npm run eval -- --only id1,id2
npm run eval -- --min-score 90   # порог прохождения (exit code 1 при провале)
npm run eval:check-refs      # без LLM: проверить эталоны на базе
```

Уровни результата: **L2** — результат совпал с эталоном; **L1** — SQL выполнился, но отличается от эталона (формулировка допускает варианты или ошибка); **L0** — не сгенерировался/упал. Целевой уровень для управленческого использования — стабильные ≥85–90% L2.

Текущее состояние: все 40 кейсов проходят на L2. Кейсы на два факта (план/факт, факторный анализ) покрыты IR v2 (подпланы + join + expr), фильтры «мера против меры» и поверх latest_snapshot-корректны по построению компилятора.

Новый кейс: объект в `questions.json` с `id`, `level`, `question` (формулировка должна фиксировать формат: порядок колонок, округление, формат месяца) и `reference_sql`. Эталон проверяется командой `npm run eval:check-refs`. Прогоняйте eval после каждой правки промпта, модели или слоя метрик — это регрессионный тест качества.

## Безопасность

- `execute_sql` принимает только одиночные `SELECT`/`WITH`/`EXPLAIN`/`VALUES`/`TABLE`: на входе — проверка (`src/guard.js`), на уровне подключения — `default_transaction_read_only=on` и `statement_timeout=15s`.
- `nl_to_sql` тоже прогоняет сгенерированный SQL через guard.
- После генерации план валидируется схемой (`src/ir.js`), а компилятор выводит SQL только из сущностей семантического слоя: неизвестные меры/измерения, значения вне доменов и недостижимые по реестру связей джойны — отказ с причиной и один исправляющий повтор LLM. Готовый SQL дополнительно прогоняется через read-only guard (`src/guard.js`).
- LLM может генерировать неверный план — проверяйте запрос перед выполнением.

## Структура

```
mcp-server/
  src/
    index.js           — MCP-сервер (stdio), инструменты, pool подключений
    llm.js             — клиент Moonshot + системный промпт (ответ = план IR) + разбор JSON
    ir.js              — строгая zod-схема плана и его валидация
    compiler.js        — детерминированная компиляция плана в SQL через @polyglot-sql/sdk
    cache.js           — файл-кэш «вопрос -> SQL» (детерминированность повторных ответов)
    trace.js           — файл-трассировка nl_to_sql (включается NL2SQL_TRACE)
    schema.js          — интроспекция схемы + статичный fallback
    semantic.js        — загрузка YAML-моделей + рендер семантического ядра
    examples.js        — few-shot примеры «вопрос -> SQL» из eval/questions.json для промпта
    validate.js        — пост-валидация свободного SQL (не используется на IR-пути; сохранена для fallback)
    models/*.yaml      — модели таблиц: измерения (sql/requires_join/domain), меры, синонимы
    relationships.yaml — реестр связей для JOIN
    guard.js           — read-only проверка SQL
  test/ir.js             — юнит-тест схемы IR (src/ir.js)
  test/compiler.js       — юнит-тест компилятора: детерминизм, отказы, выполнение на БД
  test/examples.js       — юнит-тест few-shot загрузчика (без БД и LLM)
  test/validate-joins.js — юнит-тест пост-валидации джойнов (модуль не на IR-пути)
  test/smoke.js — смоук-тест через stdio (JSON-RPC)
  test/e2e.js   — end-to-end: вопрос -> SQL -> выполнение (нужен ключ в .env)
```

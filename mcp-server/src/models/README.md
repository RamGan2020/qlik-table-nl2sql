# Модели данных (YAML): правила заполнения

Каждый файл `src/models/*.yaml` описывает одну таблицу для системы NL → SQL. YAML — **единственный источник истины о данных**: блок моделей подмешивается в системный промпт LLM, а компилятор (`compiler.js`) использует те же файлы для построения SQL и валидации. Правка YAML применяется к следующему вопросу без перезапуска (отслеживание по mtime); битый YAML не применяется — остаётся последняя рабочая версия, warning в stderr.

Как это видит модель (`semantic.js`): каждое измерение рендерится как `name (type) — label [синонимы: ...] {значения: ...}`, каждая мера — как `мера name = <SQL> — <label>. Синонимы: ... Важно: <notes>`.

---

## Общая структура файла

```yaml
name: sales                    # имя модели-факта: sales, units, sales_plan, cashflow, ...
label: "Продажи (факт)"        # человекочитаемое название
description: "..."             # 1 строка: что это за сущность; попадает в промпт
physical:
  table: sales                 # физическая таблица
  primary_key: sale_id
  alias: s                     # опционально; стабильный алиас в SQL. Без него алиас
                               # выведется автоматически и может смениться при
                               # добавлении таблиц — для боевых моделей задавайте явно
dimensions: [...]              # измерения
measures: [...]                # меры (может быть пустым списком)
```

Имена (`name`) измерений и мер внутри одной модели не должны пересекаться: компилятор ищет сначала по измерениям, потом по мерам — при совпадении имён победит измерение.

## Поля измерения

```yaml
  - name: status              # обязательно; каноническое имя, snake_case
    label: "Статус квартиры"  # обязательно
    type: string              # см. правила type ниже; по умолчанию string
    sql: "units.status"       # опционально; SQL-выражение. Без него — колонка physical.table.name
    requires_join: ["units"]  # опционально; какие таблицы нужны для sql
    synonyms: ["..."]         # опционально; см. правила synonyms
    domain: ["available"]     # опционально; см. правила domain
    notes: "..."              # опционально; инструкция к модели, в промпте — «Важно: ...»
```

Важно: **YAML-комментарии (`#`) модель не видит** — в промпт попадают только поля. Знания вида «0 = студия» или список допустимых значений переносите в `notes`, `domain` или `synonyms`.

### type (измерение)

Допустимые значения: `string`, `integer`, `decimal`, `number`, `boolean`, `date`.

Тип не влияет на SQL напрямую — он управляет **проверкой литералов фильтров** (`compiler.js: checkValueType`):

- `integer`, `decimal`, `number` — в фильтре ожидается число (`{"op": ">", "value": 50}`), строка `"50"` будет отвергнута;
- `boolean` — ожидается `true`/`false`, не строка;
- `string` — ожидается строка;
- `date` — строка строго в формате `YYYY-MM-DD`, иначе честная ошибка (`не похоже на дату`). Диапазон дат — два фильтра `>=` и `<` (конец исключительный).

Правило выбора: ставьте тип физической колонки. Для дат — всегда `date`: это включает форматную проверку и рендер `DATE '...'`.

### synonyms (измерение)

Синонимы — **только для LLM**. Компилятор разрешает рефы строго по каноническому `name` (`resolveRef` матчит `d.name === ref`); модель по синониму должна выбрать измерение и подставить его каноническое имя в план. Отсюда правила:

- пишите русскими словами, как реально спрашивают пользователи: жаргон, аббревиатуры, разговорные формы («метраж», «ЖК», «что осталось продать» — последнее лучше в меру);
- каноническое имя дублировать не нужно — оно матчится само;
- не создавайте неоднозначность внутри модели: если синоним «средняя цена» висит на двух разных мерах, модель будет угадывать (разводите пересечения через `notes`);
- синонимы с кодами домена удобно держать на измерении со `status`: коды (`available/sold/reserved`) плюс русские переводы (`свободна/продана/бронь`) — пример в `units.yaml`;
- измерения-идентификаторы (`unit_id`, `building_id`) синонимы не нужны: по ним никто не фильтрует словами.

### domain (измерение)

Домен — **закрытый набор допустимых значений**. Два эффекта:

1. в промпте значения рендерятся в фигурных скобках `{значения: ...}` с инструкцией «значения доменов бери точно как указано»;
2. компилятор **валидирует фильтр на этапе сборки**: значение вне домена — жёсткая ошибка со списком допустимых (`checkDomain`). Это защита от опечаток модели и её «творчества».

Правила:

- значения — **точно как в БД**, с учётом регистра и пробелов; если домен говорит `строится`, а в колонке `Строится` — фильтр пользователя не найдёт строк;
- заполнять только там, где набор значений закрыт и мал: статусы, типы договоров, этапы. Для городов, адресов, названий — не заполнять (набор открытый, промпт раздувается);
- 3–10 значений — разумный максимум; при росте справочника домен убирают;
- человекочитаемый смысл кодов размещайте в `label`/`synonyms`, в `domain` — только коды;
- `in`-фильтры проверяются поэлементно: каждое значение списка обязано быть в домене.

## Поля меры

```yaml
  - name: revenue                  # обязательно; snake_case
    label: "Выручка от продаж"     # обязательно
    type: simple                   # simple | ratio | derived | latest_snapshot
    sql: "SUM(sales.price)"        # для simple/derived/latest_snapshot
    # numerator_sql / denominator_sql — вместо sql, для ratio
    requires_join: ["units"]       # опционально
    synonyms: ["..."]              # правила те же, что у измерений
    notes: "..."                   # опционально; канал инструкций к модели
```

Общее правило: формула должна быть **агрегирующей** (`SUM`, `COUNT`, `AVG`, `COUNT(*) FILTER (...)`) — план оперирует мерами на уровне групп, фильтр по мере уходит в HAVING. Колонки в формуле квалифицируйте именем таблицы (`sales.price`), не алиасом.

### type (мера)

**`simple`** (по умолчанию) — готовая агрегатная формула в `sql`.

**`derived`** — формула над агрегатами в `sql`: `SUM(a) - SUM(b)`. Компилируется как `simple`; тип существует, чтобы в YAML было видно, что мера вычисляемая. Пример: `net_cash_flow`, `cash_in_deviation` в `cashflow.yaml`.

**`ratio`** — частное двух агрегатов; вместо `sql` заполняются `numerator_sql` и `denominator_sql`. Компилятор строит `(num) / (den)` — **автоматической защиты от деления на ноль нет**. Если знаменатель может обнулиться (пустая выборка, нулевой метраж), защищайте сами: `denominator_sql: "NULLIF(SUM(units.area), 0)"`. Типовой пример: взвешенная цена за м² — `SUM(price) / SUM(area)`, никогда `AVG(price_per_m2)`. Операнды `COUNT(*)` — целые: в формулах процентов держите `100.0 *` в числителе (до деления), иначе сработает целочисленное деление и дробная часть потеряется; для нестандартных долей добавляйте предупреждение в `notes` модели.

**`latest_snapshot`** — значение последнего среза нарастающего итога; требует три поля:

```yaml
    type: latest_snapshot
    sql: "construction_progress.fact_pct"        # что берём
    snapshot_key: "construction_progress.building_id"  # по чему группируем срезы
    order_by: "construction_progress.month DESC"       # как выбираем "последний"
```

Ограничения компилятора (жёсткие, `compiler.js`): нельзя в подпланах (`with`), нельзя смешивать с агрегирующими мерами в одном запросе, нельзя с `group_by` и фильтрами по мерам; фильтр по измерению применяется к выбранному срезу. Использовать для: готовности в %, остатков на дату. Не использовать для: помесячных сумм (это `simple`).

**Оконные меры** (`OVER ()`) — это `simple` с оконной функцией в `sql` (`deals_share_pct`, `revenue_cumulative`). Компилятор не ограничивает их контекст — обязательно пишите в `notes`, при какой группировке мера корректна («работает только с group_by»), иначе модель применит её в одиночном запросе и получит мусор.

### synonyms (мера)

Те же правила, что у измерений, плюс специфика мер:

- покрывайте **денежные и количественные перефразировки**: «выручка» = «продали на» = «реализация»; «пришло денег» = «поступления»;
- у граничащих мер (выручка vs поступления, продано по статусу vs число сделок) в `notes` обязательно фиксируйте разводку — какая мера для какого вопроса (`units.sold_units` это образец хорошей заметки);
- вопросы «почему»/«на сколько отклонились» маршрутизируются по синонимам мер плана и факта: у мер плана держите синонимы «план», «запланировано».

### notes (мера)

Единственный канал, через который аналитик отдаёт модели поведенческие инструкции («Важно: ...»). Используйте для: разводки похожих мер, базиса факторного анализа («для разложения на цену и объём используй м² и цену за м²»), предупреждений об известных ловушках. Держите коротко — каждая заметка платит местом в промпте.

## Связи (relationships.yaml)

Каждая запись реестра — одно ребро графа, по которому компилятор строит JOIN:

```yaml
- from: sales.unit_id    # обязательно; "таблица.колонка" на стороне "многих" при many_to_one
  to: units.unit_id      # обязательно; "таблица.колонка" на стороне "одного"
  type: many_to_one      # обязательно: many_to_one | one_to_many
  label: "Сделка относится к квартире"   # опционально; попадает в промпт
  # role: calendar       # опционально; календарное ребро — не путь обхода BFS
```

`type` — не декорация. Компилятор строит агрегирующие запросы от факта и **отказывает при джойне «от одного ко многим»** (fanout: строки размножаются, суммы задваиваются). Нужны дети по родителю («сколько броней у каждой квартиры») — делай таблицу многой стороны моделью-фактом запроса, а не джойнь её к родителю. Обе таблицы ребра должны совпадать с `physical.table` каких-то моделей. Формат связей проверяется `npm run check-models`.

## Чек-лист перед сохранением

- [ ] `name` измерений и мер уникальны внутри модели, snake_case;
- [ ] тип измерения совпадает с физической колонкой; даты — `date`;
- [ ] агрегат в `sql` квалифицирован таблицей; `requires_join` заполнен, если формула лезет в другие таблицы;
- [ ] ratio: знаменатель защищён `NULLIF`, если может быть нулём;
- [ ] новые связи в `relationships.yaml`: формат `table.column`, обязательный `type`, таблицы известны моделям (проверяется `npm run check-models`);
- [ ] domain: значения в точности как в БД (проверить `SELECT DISTINCT` — быстрее `npm run check-models`);
- [ ] знания о данных — в полях (`notes`, `domain`), не в `#`-комментариях: они не попадают в промпт;
- [ ] синонимы без внутримодельных пересечений; пересечения с другими мерами разведены в notes;
- [ ] новые меры известных «почему»-вопросов (план/факт, отклонения) покрыты синонимами.

## Проверка

```bash
npm run check-models            # линт моделей после правки YAML: поля, синонимы, парсинг SQL, домена против БД
npm test                 # юнит-тесты компилятора/валидации
node eval/run.js --check-refs   # эталонные SQL выполняются на базе
node eval/run.js --level 3      # регрессия на сложных кейсах
NL2SQL_CACHE=0 node test/e2e.js "ваш вопрос"   # без кэша: видим эффект правки сразу
```

Правка семантики инвалидирует кэш автоматически (ключ включает семантический блок), но для однократных экспериментов кэш удобнее отключать.
